- [x] 🔴🪲✅1️⃣ **Critical** - **Root cause found and fixed: "white background" on docs page headers and gallery `orbitalFlow`/`risingEmbers` (2026-08-27).** Follow-up to the unreproduced trail-persistence report logged in the Engineering Backlog lume/media-defaults entry below. The user supplied a concrete, reproducible repro this time (docs content headers, gallery `orbitalFlow` and `risingEmbers` cards) — cross-referencing the two found the real shared cause.
  > **Solution Implemented:** Not CSS and not the backdrop shader — a JavaScript engine regression. `renderer: "auto"` (the default; used by every docs-page hero and both affected gallery presets) tries WebGPU first and falls back to WebGL2 via `_fallbackFromWebGPU()` → `_replacePresentationCanvas()`, which swaps `this.canvas` for a brand-new `<canvas>` element. That method never re-pointed the instance's `IntersectionObserver` (bound to the *old* canvas in `_bindLifecycle()`) at the replacement. A detached element never reports `isIntersecting` again, so `_visible` got stuck `false` forever and `_runFrame()` silently skipped every single frame from that point on — the canvas stayed exactly as first painted (functionally blank/transparent, reading as background-colored) while `start()`/`_running` reported everything as normal. `orbitalFlow` and `risingEmbers` are the only two built-in presets with `trail > 0`, and docs headers also set `trail: 0.34` — sparse, trail-accumulating draws made the frozen frame's absence far more visually obvious than in dense modes, which is why those specific surfaces were the ones reported. Fixed by re-targeting the observer inside `_replacePresentationCanvas()` itself (`this._io.disconnect(); this._io.observe(replacement); this._visible = true; this._lastT = null;`), removing a now-redundant duplicate re-observe block that only existed on `setRenderer()`'s GPU-failure path and never on this one. Verified in real headless Chromium: docs `guides/rendering/` header (255 avg alpha, 0% white pixels), gallery `orbitalFlow` (184–193 avg alpha) and `risingEmbers` (253 avg alpha) all render correctly post-fallback; `_visible` correctly reports `true`. Full 158-test Jest suite and the Chromium/Firefox/WebKit browser smoke suite both pass with the fix applied.
  > **After Thought:** This closes the loop on the earlier unreproduced "trail persistence makes background white" report below — same underlying regression, just not reproduced yet at that point because the earlier isolated tests always passed an explicit `renderer: "webgl2"`/`"canvas2d"`, which never touches `_fallbackFromWebGPU()` at all. The WebGPU premultiplied-alpha shader fix found during that earlier investigation remains a real, independent defect (kept fixed) but was never the cause of this report.

- [x] 🔴🪲✅1️⃣ **Critical** - **Real, confirmed cause of the white-canvas trail report: a WebGPU-only shared-uniform-buffer bug (2026-08-27).** After the cache-busting fixes above, the user reported the exact same symptom persisting: "trail persistence greater than 0 seems to do nothing but make the canvas background white." Every automated test this session had run — dense/sparse modes, Canvas 2D, WebGL2, `renderer: "auto"`'s fallback path, the exact `initHeroCompactAnimation` config — converged correctly with 0% white pixels. The common thread: this environment has no real WebGPU adapter, so `renderer: "auto"` always fell back to WebGL2 in every prior test. If the reporter's browser has real WebGPU support (increasingly the Chrome/Edge default), `"auto"` renders through the *live* WebGPU path directly, which had never been exercised.
  > **Solution Implemented:** Found by code audit, not reproduction (no WebGPU hardware in this environment). `WebGPUGlyphRenderer.surface()` (used for the trail overlay and the backdrop) and `.flush()` (used for glyph instances) all wrote their per-draw color into one shared `this.uniformBuffer` via `device.queue.writeBuffer()`, then recorded a draw referencing it — but WebGPU command buffers don't execute until `queue.submit()`, and every `writeBuffer()` call for a frame happens before that one `submit()`. Since a GPU buffer is live, shared memory (not snapshotted per draw call), every draw recorded in the frame ends up reading whichever call's data was written *last* by the time the GPU actually executes — not its own. Glyph flushing always happens last in the frame, and `flush()` writes a placeholder `[1, 1, 1, 1]` into that shared buffer (opaque white — the glyph fragment shader doesn't actually consume `uniforms.color`, it reads per-instance colors, so this value was always meant to be irrelevant). The result: trail's own draw call, and backdrop's own draw call, both silently rendered solid opaque white instead of their configured colors, on every frame that had any glyphs to draw (functionally guaranteed) — matching "does nothing but make the canvas white" exactly, and explaining why it looked like trail had no effect at all: whatever `trail`/`trailColor` was set to, the compositor drew flat white regardless. WebGL2's equivalent path never had this bug — `gl.uniform4fv()` takes effect immediately relative to `gl.drawArrays()`, with none of WebGPU's deferred-submission semantics. Fixed by giving every draw call within a frame its own uniform buffer: `_acquireUniformSlot()` hands out a `{buffer}` from a small pool (grown lazily, reset per frame in `begin()`/`_beginLoadedPass()`, reused frame-over-frame — no per-frame allocation once warmed up), so `surface()`'s and `flush()`'s writes can never land on the same physical memory. Bind-group caching, previously keyed only by a fixed `"surface"`/`"glyph:<gradientKey>"` string (implicitly assuming one shared buffer), now includes the draw's ordinal position in the frame so each cached bind group stays tied to its own slot's buffer. `setAtlas()`/`setGradient()`'s targeted single-entry cache invalidation was simplified to a full `bindGroups.clear()` (both are rare, off the per-frame path, so the coarser invalidation costs nothing meaningful).
  > **Verification:** Built a mocked WebGPU device (tracked buffer identity and content through `createBindGroup`/`writeBuffer`, since jsdom has no real WebGPU) and added a new Jest test constructing an instance with `trail: 0.34` and a gradient backdrop enabled together — matching the exact `initHeroCompactAnimation` conditions — then asserting every draw in a frame gets a distinct buffer, and that trail's buffer still holds trail's own color/alpha after the frame completes rather than glyph flush's placeholder. Confirmed the test *fails* against the pre-fix code (all 3 draws collapsed onto 1 shared buffer, exactly the defect) and *passes* with the fix. Full 159-test Jest suite and the Chromium/Firefox/WebKit browser smoke suite both green (smoke coverage still can't exercise real WebGPU rendering itself, only the fallback wiring, matching the existing note on WebGPU regression coverage elsewhere in this file).
  > **After Thought:** This is the first bug this session actually found through direct WebGPU code audit rather than through observed/reproduced browser behavior, precisely because this environment cannot run real WebGPU and every prior investigation (including the IntersectionObserver fix and the cache-busting gap) kept landing on WebGL2-fallback explanations that, while real and worth fixing, didn't match the user's persistent "still happening" report. The lesson for next time: when a report survives multiple confirmed, verified fixes, the next place to look is whichever code path automated testing in this environment structurally cannot reach — here, that was real WebGPU rendering, not caching or the fallback machinery. Still unverified against actual WebGPU hardware/drivers; if the report persists after this ships, request the reporter's exact browser/GPU so the next investigation isn't guessing at the boundary of what's testable here either.
